# 梯度一：计算机网络与基础核心 (L1 入门 ~ 1年)

### 1.1 HTTP 与 HTTPS 的核心区别是什么？TLS/SSL 握手过程？
* **【考察重点】** 网络协议安全常识、对称/非对称加密配合机制。
* **【标准解答】**
  1. **安全性**：HTTP 是明文传输，内容容易被嗅探、篡改和冒充；HTTPS 在 HTTP 与 TCP 之间加入了 SSL/TLS 协议层，提供传输加密、数据完整性校验和身份认证。
  2. **默认端口**：HTTP 默认 80；HTTPS 默认 443。
  3. **握手流程（TLS 1.2 为例）**：
     * **Client Hello**：客户端发送支持的 TLS 版本、加密套件列表、随机数 $R_c$。
     * **Server Hello**：服务端确认 TLS 版本、挑选加密套件、返回服务端数字证书（含公钥）、随机数 $R_s$。
     * **证书验证与预主密钥**：客户端校验证书合法性（CA签名/过期时间/域名）；验证通过后生成随机数“预主密钥（Pre-Master Secret）”，用服务端的公钥加密后发送给服务端。
     * **生成会话密钥**：双端用 $R_c + R_s + \text{预主密钥}$ 算出会话密钥。
     * **后续通信**：完全采用**对称加密**（性能更高）进行业务数据传输。
* **【追问】** 为什么握手用非对称加密，后续传输用对称加密？
  * *答*：非对称加密计算开销大、吞吐量低，只适合用于加密协商密钥；对称加密运算快，适合海量数据传输。

### 1.2 GET 与 POST 的区别？什么是请求的“幂等性”与“安全性”？
* **【考察重点】** RESTful 规范、网络传输安全和缓存语义。
* **【标准解答】**
  * **语义**：`GET` 用于向服务器索取资源；`POST` 用于向服务器提交数据产生新资源或执行非幂等操作。
  * **参数位置**：`GET` 参数拼接在 URL query 中，长度受浏览器/服务器限制（通常 2KB~8KB）；`POST` 数据放在请求体（Body）中，理论上无限制。
  * **安全性（Safe）**：执行多次操作**不会改变服务器上的资源状态**。`GET` 是安全的，`POST` 是不安全的。
  * **幂等性（Idempotent）**：执行一次和执行 N 次，对服务器产生的**最终资源状态是一样的**。
    * `GET`、`PUT`（全量更新）、`DELETE` 具有幂等性。
    * `POST` 连续调多次会新增多条记录，**不具备幂等性**。

### 1.3 什么是跨域（CORS）？OPTIONS 预检请求触发条件是什么？
* **【考察重点】** 浏览器的同源策略（Same-Origin Policy）及跨域解决方案。
* **【标准解答】**
  * **跨域根源**：浏览器的“同源策略”。只要协议（http/https）、域名、端口三者有任意一项不同，就产生跨域。
  * **OPTIONS 预检请求**：当请求为**非简单请求**时，浏览器会自动先发一个 `OPTIONS` 方法探测服务器是否允许该跨源调用。
  * **非简单请求触发条件**：
    1. 请求方法为 `PUT`、`DELETE`、`PATCH` 或自定义方法；
    2. Header 中包含了自定义头（如前端传的 `Authorization`、`X-Token`）；
    3. `Content-Type` 不是 `text/plain`、`multipart/form-data`、`application/x-www-form-urlencoded` 之一（例如前后端分离常用的 `application/json`）。
  * **后端解决**：在响应头返回 `Access-Control-Allow-Origin: *`、`Access-Control-Allow-Methods`、`Access-Control-Allow-Headers`，并对 OPTIONS 请求直接返回 204/200。

### 1.4 状态码 301、302、304、401、403、502、504 的具体含义？
* **【考察重点】** 协议状态码与网络排障能力。
* **【标准解答】**
  * `301 Moved Permanently`：永久重定向（浏览器会强制缓存该转向）。
  * `302 Found`：临时重定向（常用于登录跳转）。
  * `304 Not Modified`：协商缓存生效，告诉客户端直接使用本地缓存副本。
  * `401 Unauthorized`：未认证（未登录或 Token 失效/缺失）。
  * `403 Forbidden`：已认证，但无权限访问该资源。
  * `500 Internal Server Error`：后端应用代码未捕获异常抛错。
  * `502 Bad Gateway`：网关（如 Nginx）收到了上游后端服务（如 Node/Java）返回的无效响应（通常是后端进程崩溃、未启动、端口连不上）。
  * `504 Gateway Timeout`：网关连接上游服务超时（后端处理时间过长超过 Nginx `proxy_read_timeout` 限制）。

### 1.5 Node.js 事件循环（Event Loop）运行机制与宏任务/微任务顺序？
* **【考察重点】** 单线程非阻塞 I/O 的本质、异步调度执行时机。
* **【标准解答】**
  * Node.js 是单线程 JavaScript 执行，但底层由 **libuv** 提供多线程线程池（处理文件 I/O、DNS 解析、加密等复杂系统调用）。
  * **执行优先级**：
    1. 同步代码执行完毕；
    2. **微任务优先清空**：`process.nextTick`（最高优先） ➔ `Promise.then / await`；
    3. **宏任务阶段（Event Loop Phases）**：
       * **Timers**：执行 `setTimeout`、`setInterval` 回调；
       * **Pending callbacks**：执行某些系统调用的回调；
       * **Idle, prepare**：内部使用；
       * **Poll（轮询）**：检索新的 I/O 事件，执行 I/O 相关回调（核心阶段）；
       * **Check**：执行 `setImmediate` 回调；
       * **Close callbacks**：执行 `socket.on('close')` 等关闭事件回调。
  * *关键点*：每当一个宏任务执行完毕或在阶段切换时，微任务队列都会被立即检查并一次性清空。

# 梯度二：工程实践与框架进阶 (L2 进阶 1 ~ 3年)

### 2.1 什么是控制反转（IoC）与依赖注入（DI）？解决什么痛点？
* **【考察重点】** 现代后端设计模式、代码解耦与单元测试友好度。
* **【标准解答】**
  * **IoC（Inversion of Control，控制反转）**：把对象的创建、组装和生命周期的控制权，从类代码内部硬编码（`new Service()`）移交给了框架容器（Container）。
  * **DI（Dependency Injection，依赖注入）**：IoC 的一种具体实现手段。类只需要声明“我需要什么依赖”，由容器在运行时自动查找并“注入”进来。
  * **解决痛点**：
    1. **解耦**：上层模块不再依赖具体实现类，只依赖抽象接口；
    2. **易于测试**：单元测试时，可以随时传入 Mock 对象（如 MockRepository），无需启动真实数据库；
    3. **单例与资源复用**：全局管理实例生命周期，避免重复构建消耗内存。

### 2.2 NestJS 中 Middleware、Guard、Interceptor、Pipe、Filter 的执行顺序与分工？
* **【考察重点】** NestJS / 洋葱模型请求生命周期管线设计。
* **【标准解答】**
  
  ```
  客户端请求 
    ⬇
  Middleware (中间件: 日志/跨域/请求体解析)
    ⬇
  Guard (守卫: 鉴权与权限校验 JWT / RBAC)
    ⬇
  Interceptor (拦截器 - 前置阶段: 计算耗时/修改入参)
    ⬇
  Pipe (管道: DTO 格式校验与类型转换 class-validator)
    ⬇
  Controller & Service (业务逻辑执行)
    ⬇
  Interceptor (拦截器 - 后置阶段: 统一包装返回数据 {code, data, msg})
    ⬇
  Exception Filter (异常过滤器: 捕获全局报错, 输出友好错误响应)
    ⬇
  客户端响应
  ```

### 2.3 为什么推荐使用 Access Token + Refresh Token 双令牌机制？
* **【考察重点】** 既要保障鉴权高效（无状态），又要兼顾凭证泄露的安全可控。
* **【标准解答】**
  * **核心痛点**：
    * JWT 是无状态的，一旦签发，在有效期内无法主动注销或作废（除非维护庞大的黑名单）；
    * 如果把 Token 有效期设得很长（如 30 天），一旦被窃取，系统毫无招架之力；
    * 如果把 Token 有效期设得很短（如 15 分钟），用户每隔 15 分钟就被踢出登录，体验极差。
  * **双 Token 解决方案**：
    * **Access Token**：有效期短（如 15~30 分钟），用于接口请求认证。权限要求高、随时轮换。
    * **Refresh Token**：有效期长（如 7~14 天），仅用于到期时换取新的 Access Token。存放在服务端 Redis 或安全 HTTP-Only Cookie 中。
    * **安全作废**：当用户点击注销或修改密码时，服务端只需在 Redis 中删除该用户的 Refresh Token，旧 Access Token 最多十几分钟后就彻底失效，实现主动踢出。

### 2.4 关系型数据库 INNER JOIN、LEFT JOIN、RIGHT JOIN、FULL JOIN 的区别？
* **【考察重点】** SQL 联表查询基础与数据集合运算。
* **【标准解答】**
  * `INNER JOIN（内连接）`：只返回两张表中连接条件**同时匹配**的交集记录。
  * `LEFT JOIN（左外连接）`：以左表为基准，返回左表**所有记录**；右表没有匹配记录的字段全部填充 `NULL`。
  * `RIGHT JOIN（右外连接）`：以右表为基准，返回右表所有记录；左表不匹配则填 `NULL`。
  * `FULL OUTER JOIN（全外连接）`：只要其中一个表存在匹配就返回记录，两边不匹配的各补 `NULL`。

### 2.5 为什么附件推荐存对象存储（MinIO / OSS / S3）而不是直接放服务器磁盘？
* **【考察重点】** 后端无状态架构（Stateless）、水平扩展与文件吞吐。
* **【标准解答】**
  1. **服务水平扩展受阻**：如果文件保存在服务器 A 的本地磁盘上，当后端扩展为多台集群（A、B、C）并挂在 Nginx 负载均衡后面时，用户下次请求打到服务器 B，就找不到上传的文件了。
  2. **磁盘空间瓶颈与备份繁琐**：应用服务器磁盘容量有限，扩容需要停机挂盘；对象存储支持弹性扩容、跨机房冷热备份、版本控制。
  3. **降低应用服务器负载**：图片和视频属于大吞吐 I/O，通过对象存储或 CDN 直接向客户端提供下载，避免消耗 Node/Java 后端的工作线程和网络带宽。

# 梯度三：缓存深度与数据库性能调优 (L3 资深 3 ~ 5年)

### 3.1 Redis 缓存三大问题：穿透、击穿、雪崩的原因与全套解决方案？
* **【考察重点】** 高并发下缓存防御机制、生产重大事故避坑。
* **【标准解答】**
  
| 场景 | 根本原因 | 现象 | 最佳解决方案 |
| :--- | :--- | :--- | :--- |
| **缓存穿透** | 查询一个**数据库中根本不存在**的数据（如黑客恶意拿 `id = -1` 刷接口） | 请求绕过 Redis 直接打向 DB，两层都没命中，DB 承受高压 | 1. **缓存空值/默认对象**（过期时间设短点，如 60s）；<br>2. **布隆过滤器（Bloom Filter）** 在 Redis 前置拦截；<br>3. 接口参数严格校验。 |
| **缓存击穿** | 某一个**超高并发热点 Key** 在某一时刻**刚好过期失效** | 瞬间成千上万个并发请求同时打向 DB 去加载数据 | 1. **分布式互斥锁**：只允许抢到锁的一个请求去查 DB 回填，其余请求重试；<br>2. **逻辑永不过期**：后台异步线程定期刷新 Key 有效期。 |
| **缓存雪崩** | **大量不同 Key 集中在同一时间段集体过期**，或 Redis 节点宕机 | 海量请求集中涌向数据库，DB 瞬间被打死崩溃 | 1. **失效时间加随机偏移量**（如基础 30 分钟 + 随机 1~5 分钟）；<br>2. **搭建 Redis 高可用哨兵/集群架构**；<br>3. 核心接口做降级与熔断（限流排队）。 |

---

### 3.2 Redis 分布式锁是如何实现的？有哪些致命坑？
* **【考察重点】** 并发互斥原子性、锁超时续期（Watchdog）与误删锁防范。
* **【标准解答】**
  1. **加锁命令**：
     ```bash
     SET lock_key unique_request_id NX PX 30000
     ```
     * `NX`：键不存在才设置（保证互斥）；
     * `PX 30000`：设置毫秒级过期时间（**必须加过期时间**，防止进程崩溃导致死锁）；
     * `unique_request_id`：必须传入客户端生成的唯一随机标识（如 UUID），**防止锁被别的线程误释放**。
  2. **释放锁命令（必须使用 Lua 脚本保证原子性）**：
     ```lua
     if redis.call("get", KEYS[1]) == ARGV[1] then
         return redis.call("del", KEYS[1])
     else
         return 0
     end
     ```
  3. **生产中的致命坑**：
     * **业务执行耗时 > 锁过期时间**：锁过期被自动释放，此时第二个线程抢到锁，第一个线程执行完会误删第二个线程的锁。
     * *解决办法*：增加**看门狗（Watchdog）自动续期机制**，在后台启动定时器，每隔锁周期的 1/3 检查一次，如果业务未结束则重置过期时间（Redisson 框架已默认实现）。

---

### 3.3 数据库事务 ACID 特性与 4 大隔离级别？脏读、幻读如何解决？
* **【考察重点】** 事务原理与并发控制机制（MVCC 与锁）。
* **【标准解答】**
  * **ACID**：
    * **A（Atomicity 原子性）**：通过 Undo Log 实现，操作要么全成功要么全回滚；
    * **C（Consistency 一致性）**：事务前后数据库状态必须满足约束，是事务的最终目标；
    * **I（Isolation 隔离性）**：并发事务互不干扰，通过 MVCC（多版本并发控制）+ 锁机制保证；
    * **D（Durability 持久性）**：通过 Redo Log 实现，事务提交后修改永久保存。
  * **4 大隔离级别与解决问题**：
    1. **读未提交（Read Uncommitted）**：会发生**脏读**（读到别人没提交的草稿数据）。
    2. **读已提交（Read Committed, RC）**：解决脏读；存在**不可重复读**（同事务内两次读取同一行数据，值被别人改了）。
    3. **可重复读（Repeatable Read, RR）**：解决不可重复读；在标准定义下可能存在**幻读**（同事务内两次范围查询，记录数变多了）。*注：PostgreSQL 和 MySQL InnoDB 通过 Next-Key Lock 和 MVCC 快照读很大程度上解决了幻读*。
    4. **串行化（Serializable）**：全加锁排队，最高安全，性能最低。

---

### 3.4 为什么数据库索引使用 B+ 树而不是二叉查找树、红黑树或 B 树？
* **【考察重点】** 磁盘 I/O 代价、数据结构与存储引擎底层的匹配逻辑。
* **【标准解答】**
  1. **不选二叉树/红黑树**：
     * 二叉树每个节点只有 2 个孩子，树的高度非常深（若有 1000 万条数据，红黑树高度约 24 层）；
     * 每次深入下一层树节点就是一次**磁盘寻道 I/O**（毫秒级极慢），树太高会导致 I/O 次数爆炸。
  2. **B+ 树 vs B 树（为什么 B+ 树更优？）**：
     * **非叶子节点不存数据，只存索引 Key**：由于节点大小固定（如一页 16KB），不存具体数据意味着一个节点能容纳更多分支指针，**使树更加矮胖（通常 3~4 层即可存储几千万条数据，只需 3~4 次 I/O）**。
     * **叶子节点包含全部数据且使用双向链表相连**：极度利于**范围查询（Range Query）**和排序。B 树的范围查询必须通过中序遍历回溯父子节点，开销巨大。
     * **查询性能更稳定**：任何记录的查找都必须走到叶子节点，路径长度一致。

---

### 3.5 慢 SQL 如何定位？EXPLAIN 执行计划看哪些核心指标？深分页如何优化？
* **【考察重点】** SQL 调优基本功与大表查询排障手段。
* **【标准解答】**
  1. **定位慢 SQL**：开启数据库慢查询日志（Slow Query Log），设定阈值（如超过 500ms），结合 APM 链路追踪。
  2. **EXPLAIN 核心字段指标**：
     * **type（访问类型，性能从差到好）**：`ALL`（全表扫描 ❌）➔ `index`（全索引扫描）➔ `range`（范围匹配）➔ `ref`（普通索引匹配）➔ `eq_ref`（唯一索引关联）➔ `const`（常量级命中 ✅）。要求至少达到 `range` 级别。
     * **possible_keys & key**：预计使用的索引与实际命中的索引。
     * **rows**：预估需要扫描检查的行数（越小越好）。
     * **Extra**：
       * 出现 `Using filesort`：使用了额外外部文件排序，需建立组合索引优化；
       * 出现 `Using index`：命中**覆盖索引**（无需回表，性能极佳）。
  3. **深分页优化（如 `LIMIT 1000000, 10`）**：
     * **痛点**：数据库需要扫描前 1000010 条记录并抛弃前 100 万条，产生大量无用的回表 I/O。
     * **优化方案 1（延迟关联/子查询）**：先只查索引主键，再根据主键关联查内容：
       ```sql
       SELECT * FROM t JOIN (SELECT id FROM t ORDER BY id LIMIT 1000000, 10) temp ON t.id = temp.id;
       ```
     * **优化方案 2（游标分页/标签法）**：记录上一页最后一条的主键 ID：
       ```sql
       SELECT * FROM t WHERE id > 1000000 ORDER BY id ASC LIMIT 10;
       ```

# 梯度四：高并发与分布式核心 (L4 专家 5年+)

### 4.1 引入消息队列（MQ）的作用？如何保证消息不丢失与消费幂等？
* **【考察重点】** 分布式消息系统可靠性传输三要素。
* **【标准解答】**
  * **三大作用**：**解耦**（业务上下游解约）、**异步**（非关键流程异步化加速响应）、**削峰填谷**（突发流量缓冲）。
  * **如何保证消息 100% 不丢失？**
    1. **生产端防丢**：开启 Confirm 确认机制，直到收到 Broker 的 ACK 响应才算成功；如果超时或收到 NACK 则进行重试。
    2. **Broker 存储端防丢**：将队列持久化（durable），开启磁盘同步刷盘机制；集群部署主从同步（至少写入多个副本节点再返回成功）。
    3. **消费端防丢**：关闭自动 ACK（autoAck=false），待业务逻辑全部成功处理完毕后，再手动向 Broker 发送 ACK。
  * **如何保证消息消费的幂等性（防重复消费）？**
    * 每条消息在生产时附带唯一的 `message_id` 或业务流水号（如 `order_no`）；
    * 消费端使用 Redis `SETNX` 或数据库**唯一索引（Unique Constraint）**进行防重校验：如果已处理过则直接返回成功丢弃消息。

---

### 4.2 CAP 定理与 BASE 理论？实际微服务中如何抉择？
* **【考察重点】** 分布式系统设计顶层哲学。
* **【标准解答】**
  * **CAP 定理**：
    * **C（Consistency 一致性）**：所有节点在同一时刻看到的数据完全一致；
    * **A（Availability 可用性）**：每个请求都能在合理时间内得到成功/失败的响应，不发生阻塞；
    * **P（Partition tolerance 分区容错性）**：当网络出现故障切断导致节点分裂时，系统仍能继续运作。
  * **铁律**：**分布式系统在网络分区（P）必然存在的前提下，只能在 CP 与 AP 之间二选一**。
    * **CP 架构（如 ZooKeeper / Etcd / 银行核心结算）**：优先保证数据绝对正确，分区时拒绝服务以防脏读。
    * **AP 架构（如 Eureka / 多数互联网高并发业务）**：优先保证服务不宕机，允许短时间内数据存在微小差异。
  * **BASE 理论（AP 的延展）**：
    * **Basically Available（基本可用）**：响应时间可以稍微增加，核心功能正常。
    * **Soft State（软状态）**：允许系统中存在中间状态。
    * **Eventually Consistent（最终一致性）**：经过一段时间同步后，所有节点数据最终达到一致状态。

---

### 4.3 分布式事务有哪些常见落地方案？
* **【考察重点】** 跨库/跨服务数据一致性终极解法。
* **【标准解答】**
  1. **2PC（两阶段提交） / 3PC**：强一致性方案（准备阶段 ➔ 提交阶段），由协调者推动。性能低下、阻塞长，互联网高并发场景极少使用。
  2. **TCC（Try-Confirm-Cancel）**：业务侵入型柔性事务。
     * `Try`：预留资源（如冻结账户 100 元）；
     * `Confirm`：确认执行业务（正式扣款 100 元）；
     * `Cancel`：取消操作回滚预留资源（解冻 100 元）。
  3. **本地消息表 + MQ 最终一致性（最推荐落地方案）**：
     * 在同一个本地数据库事务中，**保存业务数据的同时向本地 `msg_log` 表插入一条“待发送”消息**；
     * 由后台定时任务或事务监听轮询抓取 `msg_log` 发送到 MQ；
     * 下游系统消费 MQ 成功后发确认指令，上游标记本地消息为“已完成”。即使 MQ 或下游系统短时故障，也能持续重试保障最终一致。
  4. **Saga 模式**：长事务拆分成一系列本地事务，若某一步失败，按反向顺序依次调用各服务的补偿接口（如 Seata Saga）。

### 4.4 分布式唯一 ID 生成策略有哪些（UUID、Snowflake、Redis）？优缺点对比？
* **【考察重点】** 分布式主键有序性与生成性能对比。
* **【标准解答】**
  
| 方案 | 原理 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **UUID** | 本地基于 MAC+时间戳随机生成 36 位字符串 | 本地生成速度极快、无中心化单点瓶颈 | 字符串太长且**完全无序**，作为 MySQL 聚簇索引会导致频繁的 **B+ 树页分裂**，严重损耗插入性能 |
| **Redis `INCR`** | 利用 Redis 单线程原子计数 | 纯数值自增、全局严格有序、性能高 | 强依赖 Redis 实例稳定性，网络抖动或主从切换可能带来重复或阻塞 |
| **Snowflake（雪花算法）** | 64 位 long 型数值：1 位符号 + 41 位时间戳 + 10 位机器标识 + 12 位序列号 | **全局趋势自增**、不依赖第三方、性能极高（单机单毫秒可生成 4096 个 ID） | **强依赖系统时钟**；若服务器发生“时钟回拨”，可能生成重复 ID（需代码实现时钟回拨校验与缓冲等待） |

# 梯度五：系统设计与高可用架构实战 (L5 架构/场景题)

### 5.1 场景题：如何设计一个抗住十万 QPS 的电商秒杀系统？
* **【考察重点】** 分层防御（漏斗模型）、动静分离、热点隔离与防超卖。
* **【标准架构答题套路】**

```
              用户海量请求 (10万 QPS)
                         ⬇
  【客户端层】按钮点击防抖置灰 + 动态验证码（分散瞬时峰值）
                         ⬇
  【CDN / 网关层】秒杀详情页面动静分离；Nginx 限流（IP黑名单/漏桶）
                         ⬇
  【应用层】隐藏秒杀 URL（只有活动开始才下发带哈希的路径）；本地内存标记（布隆/标志位拦截已售罄商品）
                         ⬇
  【缓存层】Redis 预减库存（通过 Lua 脚本原子执行 decr + 判断库存是否 < 0）
                         ⬇ (仅放行与库存相匹配的极少数有效请求, 如前 1000 个)
  【消息队列】RabbitMQ / Kafka 异步削峰排队
                         ⬇
  【数据库层】单线程或批量消费：UPDATE stock SET count = count - 1 WHERE id = 1 AND count > 0;
```

* **防超卖核心原则**：
  * **不要在数据库中直接扛秒杀**；
  * 先在 Redis 执行 Lua 脚本扣除内存库存；
  * 数据库最后一道防线使用乐观锁加行级底线：`WHERE stock > 0`。

---

### 5.2 场景题：接口防重（幂等性）如何落地设计？
* **【考察重点】** 表单重复提交、网络重试导致的数据多扣/多增处理。
* **【标准解决方案】**
  1. **Token 令牌机制（最通用）**：
     * 用户进入表单页面时，前端先请求一个全局唯一的 `submit_token`，后端放入 Redis 并设置短期过期时间；
     * 用户提交表单时携带该 `submit_token`；
     * 后端用 Lua 脚本执行 `if redis.call('get', token) then return redis.call('del', token) else return 0 end`；
     * 若能成功删除 Token 说明是第一次提交，放行业务；若返回 0 说明是重复提交，直接拒绝。
  2. **数据库唯一索引（底层托底）**：
     * 为业务表添加唯一复合索引（例如 `unique_key: user_id + biz_type + out_trade_no`）；
     * 重复插入触发 `Duplicate entry` 报错并优雅吞掉异常。
  3. **防重状态机（针对更新操作）**：
     * `UPDATE orders SET status = 'PAID' WHERE order_no = 123 AND status = 'UNPAID';`
     * 无论调用多少次，只有符合初始状态的才能更新成功。

### 5.3 常见服务限流算法有哪些？各自原理与适用场景？
* **【考察重点】** 流量削峰、高可用防御体系。
* **【标准解答】**
  1. **固定窗口计数器**：
     * *原理*：按时间窗口（如每秒）计数，超过阈值则拦截，下一个周期重置。
     * *缺陷*：**临界窗口突发翻倍问题**（前一秒的后 500ms 来了 100 个，后一秒的前 500ms 来了 100 个，在 1 秒区间内实际上涌入了 200 个）。
  2. **滑动窗口计数器（Sliding Window）**：
     * *原理*：把大时间窗口细分为多个小格（如 1 秒拆分为 10 个 100ms），随时间向右平移。平滑了窗口临界突变问题。
  3. **漏桶算法（Leaky Bucket）**：
     * *原理*：请求像水一样流入水桶，水桶底部以**绝对恒定的速率**往外滴水（处理）。
     * *特点*：能够强行将突发流量平滑为平稳输出，但**无法应对正常的突发突量**。
  4. **令牌桶算法（Token Bucket - 最推荐，如 Google Guava RateLimiter）**：
     * *原理*：系统以恒定速率向容量有限的桶中投放令牌，桶满则溢出；每个请求必须拿到令牌才可执行。
     * *优点*：**既能限制平均并发速率，又允许在桶内有积累令牌时短时间内承受一定的突发流量**。
